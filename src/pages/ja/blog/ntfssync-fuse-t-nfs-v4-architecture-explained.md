macOS上で非ネイティブなファイルシステム（NTFS、ext4、SSHFS、各種クラウドストレージのマウントなど）を扱ったり開発したりした経験のある方なら、誰しも **FUSE（Filesystem in Userspace: ユーザー空間ファイルシステム）** という名前に聞き覚えがあるはずです。

Macの世界では長年にわたり osxfuse（後の macFUSE）が標準として使われてきました。しかし、AppleがApple Siliconチップへと移行し、macOSのカーネル拡張機能（`.kext`）に対する規制を急速に強化したことで、macFUSEは大きな壁に突き当たりました。OSのメジャーアップデートのたびにMacをRecoveryモードで起動し、システム整合性保護（SIP）を緩め、セキュリティポリシーを引き下げなければ動作しなくなったのです。

その閉塞感を打ち破った革新的な技術が **FUSE-T** です。

本記事では、[NTFSSync](https://apps.apple.com/app/id6475194342) の中核エンジンに採用されている **FUSE-T ＋ ローカルループバック NFS v4** アーキテクチャの内部構造を深掘りし、カーネルに1行のコードも注入することなく、いかにしてネイティブ級の転送速度と絶対的なシステム安全性を両立しているのかを解説します。

## 従来の macFUSE が抱えていた構造的ジレンマ

FUSE-Tの先進性を理解するために、まずは従来のmacFUSEの仕組みを振り返ってみましょう。

従来のFUSEは、大きく分けて2つのコンポーネントで成り立っていました。
1. **ユーザー空間ライブラリ（`libfuse`）**：NTFSのディレクトリツリーやメタデータを解析するユーザー空間プロセス。
2. **カーネル拡張機能（`fuse.kext`）**：macOSのVFS（仮想ファイルシステム層）とユーザー空間プロセスの橋渡しを行うカーネル内モジュール。

ユーザーがFinder上でファイルを読み書きする際、呼び出しの流れは以下のようになります。  
`Finder` → `VFS (カーネル層)` → `fuse.kext (カーネル層)` → `プロセス間通信 (IPC)` → `ユーザー空間NTFSデーモン` → `物理USB/SSDセクタのI/O`

この設計には2つの深刻な問題がありました。
- **macOSのセキュリティ方針との根本的衝突**：Appleはサードパーティ製kextを完全にレガシー扱いとして排除を進めています。`fuse.kext` を読み込ませるためだけに、ユーザーはシステムのハードウェア保護を「低減されたセキュリティ」へと落とさざるを得ません。
- **コンテキストスイッチ（Context Switch）のオーバーヘッド**：ファイルI/OのたびにRing 0（カーネル空間）とRing 3（ユーザー空間）を往復するため、小ファイルの大量コピー時にCPU負荷が増大し、転送性能が著しく低下します。

## FUSE-Tの画期的な発想：OS標準の「NFS v4」スタックを逆手に取る

FUSE-Tの開発者は、きわめて独創的かつ実用的な問いを立てました。

> *「Appleのカーネル内には、何十年も磨き上げられ、極限まで最適化された公式ファイルシステムクライアントが最初から存在している。それをそのまま再利用すれば、わざわざ自前のkextをコンパイルしてカーネルに潜り込ませる必要はないのではないか？」*

その標準クライアントこそが、**NFS（Network File System）バージョン4** です。

### FUSE-Tの内部動作メカニズム

1. **標準FUSE APIとの互換性維持**：アプリケーション層において、NTFSSyncは実績ある標準FUSEインターフェースを用いてNTFSフォーマットのパース、キャッシュ管理、ダーティビット制御を行います。
2. **インプロセス超軽量NFSサーバーの起動**：FUSE-Tはユーザー空間内で超軽量なNFS v4サーバーを立ち上げます。これはローカルループバックアドレス（`127.0.0.1`）の動的ランダムポートにのみバインドされるため、外部ネットワークからは完全に遮断されており安全です。
3. **macOS標準の `/sbin/mount_nfs` によるマウント**：外付けNTFSドライブが接続されると、macOS標準のシステムコマンドが `127.0.0.1` に対して実行され、Finderからは通常のローカルボリュームと何ら変わらない形でマウントされます。

```
[ アプリケーション（Finder / Terminal / 編集ソフト） ]
                        │
                        ▼
[ macOS カーネル VFS層（Apple公式ネイティブコード） ]
                        │（標準 NFS v4 クライアント）
                        ▼
[ ローカルループバック通信（127.0.0.1） ]
                        │
                        ▼
[ FUSE-T ユーザー空間デーモン（NTFSSync プロセス） ]
                        │
                        ▼
[ libntfs-3g 解析エンジン ＆ ブロックデバイスドライバ ]
                        │
                        ▼
[ 外付け USB / NVMe ポータブルSSD / ハードディスク ]
```

## 性能検証：ループバック通信によるオーバーヘッドはあるのか？

エンジニアが真っ先に抱く疑問は、「ディスクI/OをTCP/IPループバックソケット経由で処理すると、ダイレクトなカーネルドライバーより遅くなるのではないか？」という点でしょう。

結論から言うと、**実測ベンチマークにおいて極めて高速であり、従来のkextドライバーと同等以上の実効スループットを叩き出します**。

その理由は以下の3点に集約されます。

1. **XNUカーネル内でのループバック高速バイパス**：macOSのループバック通信（`127.0.0.1`）は、物理NICのハードウェア処理を完全にスキップし、システムメモリ（RAM）内のバッファコピーとして直接処理されます。
2. **NFS v4のコンパウンドRPC（Compound RPC）**：従来のプロトコルと異なり、NFS v4は `LOOKUP`、`GETATTR`、`OPEN` などの複数操作を1つのリクエストにまとめて送信できます。往復のレイテンシが極小化され、メタデータ処理が高速に行われます。
3. **macOSカーネルのページキャッシュ機構**：Apple純正のNFSクライアントは、非同期先読み（Read-ahead）および遅延書き込み（Write-behind）キャッシュが極めて洗練されています。外付けUSB 3.2 Gen 2対応のNVMe SSDを接続した場合、NTFSSyncは **実測400MB/s〜900MB/s** の高スループットを維持し、物理バスの帯域幅を限界まで引き出します。

## エンドユーザーにとっての計り知れないメリット

この洗練されたアーキテクチャは、日々の作業環境において以下のような絶大なメリットをもたらします。

- **カーネルパニックによるOS巻き込み死の完全防止**：仮に外付けドライブに物理的な不良セクタが存在したり、コピー中にUSBケーブルを急に引き抜かれたりしても、影響は隔離されたユーザー空間プロセス内で安全に処理されます。Mac全体がフリーズしたり、突然再起動したりすることは構造上あり得ません。
- **システムのセキュリティ水準を一切落とさない**：電源ボタン長押しでRecoveryモードに入る必要も、起動セキュリティユーティリティでセキュリティレベルを下げる必要もありません。Mac本来の完全な保護が維持されます。
- **企業のMDM監査に100%適合**：サードパーティ製カーネル拡張機能を一律禁止している企業管理下のMac（Jamf、Intune等）でも、何ら制約なく導入可能です。
