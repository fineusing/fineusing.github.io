幾乎每一位 Mac 使用者都在下載完重要檔案後，見過蘋果系統內建封存工具彈出的這個「經典惡魔彈窗」：

```text
無法將「archive.zip」展開至「下載」。
（錯誤 79 - 不適用的檔案或操作）
```

這是 macOS 系統中最令人抓狂的報錯之一。因為蘋果的提示語極其含糊，根本不告訴使用者到底是哪裡出了問題：
- 是檔案下載時損壞了？
- 是網路中斷少了一截？
- 是檔案本身設定了密碼？
- 還是蘋果內建的解壓縮工具能力不足？

根據我們在數千個實際案例中的技術統計分析：**超過 90% 觸發「錯誤 79」的壓縮檔，其內部資料其實完好無損。** 真實的原因是蘋果內建的「封存工具程式（Archive Utility）」在面對現代複合型壓縮檔時，容錯與解析能力嚴重落後。

今天我們把觸發「錯誤 79」的四大真實技術成因逐一拆解，並分享如何將其順利且完整地解壓縮。

## 錯誤 79 底層觸發的 4 大真實技術元兇

macOS 內建的封存工具底層封裝自歷史悠久的 `libarchive` 與系統私有架構。一旦二進位資料流稍微偏離了蘋果預設的狹窄標準，底層 POSIX 系統呼叫就會立刻拋出 `EINVAL` 錯誤代碼（對應編號：Error 79，意為 Invalid Argument 不適用的引數/格式）。

### 1. 超大檔案的 ZIP64 格式位移相容性問題
原始的舊版 ZIP 規範有兩大物理上限：單一壓縮檔容量不能超過 4GB、檔案數量不能超過 65,535 個。為了打破這一限制，業界推出了 **ZIP64** 擴充規範。
WinRAR、7-Zip 或 Python 等工具在寫入超大檔案包時，若將 ZIP64 的額外中繼資料欄位存放在中央目錄的特定位置，macOS 封存工具程式在定位 64 位元偏移量時經常會計算越界，當場跳出錯誤 79。

### 2. 誤將分割壓縮檔（如 `.z01`、`.7z.001`）當作獨立包連按兩下
如果他人傳來的是一套分割壓縮檔（例如 `backup.z01`、`backup.z02`、`backup.zip`），很多使用者習慣性去連按兩下排在最前面的 `backup.z01`。
蘋果系統內建工具完全沒有多卷自動定址串聯機制。它讀取該檔案時發現尾部缺失完整的中央目錄索引，便誤以為檔案嚴重損毀，立刻拋出錯誤 79。

### 3. ZIP 容器內採用了特殊壓縮編碼（Deflate64、LZMA2 等）
`.zip` 只是一個外殼容器。在這個容器內部，壓縮資料可以用不同的壓縮演算法編碼：
- 標準 `Deflate`（演算法編號 8）：蘋果原生支援良好；
- `Deflate64`（演算法編號 9）：常見於某些 Windows 壓縮工具或舊版 7-Zip，蘋果內建工具經常無法解析；
- `Bzip2`（編號 12）或 `LZMA`（編號 14）：用於實現極限高壓縮比。
當內建工具在檔案標頭讀到不認識的演算法編號時，由於缺少對應的解碼器，也會拋出錯誤 79。

### 4. 7Z / RAR5 開啟了「加密檔案名稱」功能
當製作者在打包 7Z 或 RAR5 時勾選了「加密檔案名稱」，整個檔案的目錄樹與所有檔案名稱清單全部被高強度加密金鑰包覆。蘋果內建工具甚至無法預先讀取包內包含什麼檔案類型，就會誤判定該檔案「格式無效」。

## 為什麼終端機 `unzip` 指令也經常無法挽救？

遇到錯誤 79 時，網路上常見教學會建議打開終端機執行 `unzip archive.zip`。

但往往終端機也隨之報出一串紅字：
```text
warning: extra bytes at beginning or within zipfile
error: cannot find zipfile directory
unsupported compression method 9
```
原因在於蘋果 macOS 預載的終端機 `unzip` 二進位程式基於古老的 Info-ZIP 原始碼，已經超過十年沒有核心大版本迭代。它對於現代複雜的串流修復、多卷融合與新型編碼同樣缺乏支援。
