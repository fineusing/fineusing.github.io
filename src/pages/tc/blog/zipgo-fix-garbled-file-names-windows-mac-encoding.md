## 亂碼的根源：macOS UTF-8 與 Windows 歷史字碼頁的衝突

這個問題的根本原因，在於兩個作業系統在處理檔案名稱壓縮時採取了不同的字元集標準：

1. **macOS 全面採用 Unicode（UTF-8）**：蘋果從早期的 OS X 到如今最新的 macOS 系統，檔案系統（APFS / HFS+）與底層工具一律預設使用嚴格的 UTF-8 編碼。
2. **Windows ZIP 壓縮機制沿用傳統字碼頁（Code Page）**：在 Windows 檔案總管內建的壓縮功能或某些老舊打包工具中，產生 ZIP 包時並沒有強制標記 UTF-8 標誌位元，而是直接按照目前系統的本機 ANSI 字碼頁寫入位元組流：
   - **繁體中文（台灣/香港）Windows**：預設採用 `CP950`（Big5）；
   - **簡體中文 Windows**：預設採用 `CP936`（相容 GBK / GB2312 / GB18030）；
   - **日本 Windows**：預設採用 `CP932`（Shift-JIS）；
   - **韓國 Windows**：預設採用 `CP949`（EUC-KR）；
   - **歐美西歐語言**：預設採用 `Windows-1252`。

當 macOS 內建的「封存工具程式」解壓縮時，它會武斷地將這些非 UTF-8 位元組流強行按 UTF-8 解碼。Big5、GBK 或 Shift-JIS 的雙位元組編碼與 UTF-8 的變長規則完全不相符，系統無法對應正確的文字，最終只能將錯亂的位元組對應成一堆拉丁重音符號、特殊符號甚至方塊問號亂碼。

## 傳統的終端機指令解法為什麼在日常工作中極難使用？

在技術論壇或 StackOverflow 上，常見的工程師解法是打開 Terminal 終端機輸入指令：

```bash
# 嘗試指定 Big5/CP950 編碼解壓
unzip -O CP950 filename.zip -d ./output_folder
```

或者針對日文壓縮包：

```bash
unzip -O Shift-JIS filename.zip -d ./output_folder
```

### 為什麼這個方案在日常極不實用？
1. **macOS 內建的 BSD `unzip` 根本不支援 `-O` 參數**：直接在 Mac 終端機執行會提示 `unzip: invalid option -- O`。你必須先安裝 Homebrew，然後再去編譯打補丁版本或安裝第三方 `unar`。
2. **你需要人工盲猜編碼**：傳送檔案給你的可能是香港設計事務所、東京廣告公司、還是其他分部？如果猜錯了字碼頁，解出來依然是另一種亂碼。
3. **遇到帶密碼或多卷分割檔直接失效**：命令列工具在處理多卷分割（`.z01`、`.7z.001`）或複雜 AES 加密時參數極其繁瑣，極易解壓縮失敗。

它無需你記住任何終端機指令，也不需要你手動選擇檔案來自哪個國家或地區：
