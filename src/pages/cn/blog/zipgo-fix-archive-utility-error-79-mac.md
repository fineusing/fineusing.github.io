几乎每一位 Mac 用户都在下载完重要文件后，见过苹果系统自带归档工具弹出的这个“经典恶魔弹窗”：

```text

```

这是 macOS 系统中最令人抓狂的报错之一。因为苹果的提示语极其含糊，根本不告诉用户到底是哪里出了问题：
- 是文件下载损坏了？
- 是网速中断少了一截？

根据我们在数千个实际案例中的技术统计分析：**超过 90% 触发“错误 79”的压缩包，其内部数据其实完好无损。** 真正的原因是苹果自带的“归档实用工具（Archive Utility）”在面对现代复合型压缩包时，容错与解析能力严重滞后。

今天我们把触发“错误 79”的四大真实技术成因扒开，并分享如何将其顺利完整解包。

## 错误 79 底层触发的 4 大真实技术元凶

macOS 自带的归档工具底层封装自历史悠久的 `libarchive` 与系统私有框架。一旦二进制数据流稍微偏离了苹果预设的狭窄标准，底层 POSIX 系统调用就会立刻抛出 `EINVAL` 错误码（对应编号：Error 79，意为 Invalid Argument 不适用的参数/格式）。

### 1. 超大文件的 ZIP64 格式位移兼容性问题
原始的旧 ZIP 规范有两大物理上限：单包体积不能超 4GB、文件数量不能超过 65,535 个。为了打破这一限制，行业推出了 **ZIP64** 扩展规范。
WinRAR、7-Zip 或 Python 等工具在写入超大包时，如果将 ZIP64 的额外元数据字段存放在中心目录的特定位置，macOS 归档工具在定位 64 位偏移时经常会计算越界，当场报出错误 79。

### 2. 误将分卷切片（如 `.z01`、`.7z.001`）当作独立包双击
如果别人发来的是一套分卷文件（例如 `backup.z01`、`backup.z02`、`backup.zip`），很多用户习惯性去双击排在最前面的 `backup.z01`。
苹果系统自带工具完全没有多卷自动寻址机制。它读取该文件时发现尾部缺失完整的中央目录索引，误以为文件严重破损，立刻抛出错误 79。

### 3. ZIP 容器内采用了冷门压缩编码（Deflate64、LZMA2 等）
`.zip` 只是一个外壳容器。在这个容器内部，压缩数据可以用不同的压缩算法编码：
- 标准 `Deflate`（算法编号 8）：苹果原生支持良好；
- `Deflate64`（算法编号 9）：常见于某些 Windows 压缩工具或老版本 7-Zip，苹果自带工具常常不支持；
- `Bzip2`（编号 12）或 `LZMA`（编号 14）：用于实现极限高压缩率。
当自带工具在文件头部读到不认识的算法编号时，由于没有对应的解码器，也会甩出错误 79。

### 4. 7Z / RAR5 开启了“加密文件名”功能
当制作者在打包 7Z 或 RAR5 时勾选了“加密文件名”，整个包的目录树和所有文件名列表全部被强加密密钥包裹。苹果自带工具甚至无法窥视包内包含什么文件类型，就会误判定该文件“格式无效”。

## 为什么终端 `unzip` 命令也经常救不回来？

遇到错误 79 时，网上常见教程会建议打开终端运行 `unzip archive.zip`。

但往往终端也随之报出一串红字：
```text
warning: extra bytes at beginning or within zipfile
error: cannot find zipfile directory
unsupported compression method 9
```
原因在于苹果 macOS 预装的终端 `unzip` 二进制程序基于古老的 Info-ZIP 源码，已经超过十年没有核心大版本迭代。它对于现代复杂的流式修复、多卷融合与新型编码同样缺乏支持。
