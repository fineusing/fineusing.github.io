## 乱码的根源：macOS UTF-8 与 Windows 历史代码页的冲突

这个问题的根本原因，在于两个操作系统在处理文件名压缩时采取了不同的字符集标准：

1. **macOS 全面采用 Unicode（UTF-8）**：苹果从早期的 OS X 到如今最新的 macOS 系统，文件系统（APFS / HFS+）和底层工具一律默认使用严格的 UTF-8 编码。
2. **Windows ZIP 压缩机制沿用传统代码页（Code Page）**：在 Windows 资源管理器自带的压缩功能或某些老旧打包工具中，生成 ZIP 包时并没有强制标记 UTF-8 标志位，而是直接按照当前系统的本地 ANSI 代码页写入字节流：
   - **简体中文 Windows**：默认采用 `CP936`（兼容 GBK / GB2312 / GB18030）；
   - **日本 Windows**：默认采用 `CP932`（Shift-JIS）；
   - **繁体中文（港台）Windows**：默认采用 `CP950`（Big5）；
   - **韩国 Windows**：默认采用 `CP949`（EUC-KR）；
   - **欧美西欧语言**：默认采用 `Windows-1252`。

当 macOS 自带的“归档实用工具”解压时，它会武断地将这些非 UTF-8 字节流强行按 UTF-8 解码。GBK 或 Shift-JIS 的双字节编码与 UTF-8 的变长规则完全不匹配，系统无法映射对应的汉字，最终只能将错乱的字节映射成一堆拉美重音符号、特殊符号甚至方块乱码（``）。

## 传统的终端命令解法为什么在日常工作中很难用？

在技术论坛或 StackOverflow 上，常见的极客方案是打开 Terminal 终端输入命令：

```bash
# 尝试指定 GBK/CP936 编码解压
unzip -O CP936 filename.zip -d ./output_folder
```

或者针对日文压缩包：

```bash
unzip -O Shift-JIS filename.zip -d ./output_folder
```

### 为什么这个方案日常极不实用？
1. **macOS 自带的 BSD `unzip` 根本不支持 `-O` 参数**：直接在 Mac 终端执行会提示 `unzip: invalid option -- O`。你必须先安装 Homebrew，然后再折腾编译打补丁版或者安装第三方 `unar`。
2. **你需要人工盲猜编码**：发给你文件的可能是深圳供应链、东京广告公司、还是台湾分部？如果猜错了代码页，执行出来依然是另外一种乱码。
3. **遇到带密码或多分卷直接哑火**：命令行工具在处理多卷拆分（`.z01`、`.7z.001`）或者复杂 AES 加密时参数极其繁琐，极易解压失败。
